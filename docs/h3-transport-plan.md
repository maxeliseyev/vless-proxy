# План: собственный транспорт поверх QUIC/HTTP/3

Статус: черновик плана, 2026-10-18. Цель не «свой протокол», а инструмент, который можно поднять на своём VPS и который ТСПУ долго не сможет описать сигнатурой. Гипотезы ниже проверяют тестировщики за DPI-заслоном, план меняется по их результатам.

## 1. Что известно о ТСПУ на октябрь 2026

Источники: разбор поведенческих блокировок на Хабре ([1047442](https://habr.com/ru/articles/1047442/), реконструкция по одному источнику, пороги это гипотезы автора), issue Xray о Chrome-отпечатке ([XTLS/Xray-core#7131](https://github.com/XTLS/Xray-core/issues/7131)), разбор Hysteria 2 ([1008554](https://habr.com/ru/articles/1008554/)), измерительная работа по ТСПУ ([Xue et al., IMC 2022](https://ensa.fi/papers/tspu-imc22.pdf)), отчёт о блокировке ECH ([ACF, март 2026](https://fbk.info/files/acf-internet-report-EN.pdf)).

Сигналы, которые ТСПУ, по этим данным, комбинирует (срабатывает сочетание, а не один признак):

| Сигнал | Что известно | Следствие для нас |
|---|---|---|
| Репутация IP/AS | Зарубежные хостеры (Hetzner, DO, OVH) давно в списке, часть российских облаков добавили в мае-июне 2026; крупные CDN не целиком | Протоколом не лечится. Проверять одну и ту же сборку с двух хостеров (гипотеза H7) |
| TLS-отпечаток | Go `crypto/tls` помечен; Chrome 133 из uTLS «целевой давно» (RPRX, 13.10.2026): для него ограничивают число соединений, иногда задевая настоящий Chrome; Chrome 155 и Firefox 148 проходят | Наш `fp=chrome` это HelloChrome_133. Обновить до 155 немедленно (стадия 0), держать цикл обновления |
| Параллельные handshake | Больше 3 одновременных TLS-соединений к одному SNI → заморозка ~120 с; смена отпечатка во время заморозки продлевает до 600 с | Одно QUIC-соединение на сервер, всё внутри мультиплексируется. Никаких «4 соединения ради скорости» |
| Объём и форма потока | Заморозка после ~16 КБ (февраль) или ~25 пакетов / 15-20 КБ (net4people) при подозрительном сочетании; симметричный ratio 1:2-1:3, нет пауз, пакеты ровно по MTU | Форма потока это отдельный фронт работ (стадия 4), сначала измерить, что именно ловят |
| QUIC | У ТСПУ есть QUIC-триггер (UDP выше порога размера с QUIC-отпечатком) ещё с 2022; ECH режут и в TLS, и в QUIC с ноября 2024; Hysteria 2 «пока самый устойчивый»; полностью режут UDP ~5% провайдеров, часть мобильных душит UDP/QUIC | QUIC не невидим, но это укрытие внутри огромного легитимного трафика HTTP/3. Без ECH (у Chrome только GREASE ECH, он проходит). Нужен TCP-запасной путь (REALITY у нас уже есть) |
| Заморозка | Не RST, а чёрная дыра после handshake по ключу (IP клиента, SNI); в логах клиента `i/o timeout` | В тестах фиксировать именно таймауты и паузу между прогонами ≥ 10 минут |

Вывод: raw UDP со случайным заголовком (catwire, WireGuard, AmneziaWG) попадает в класс «неизвестный UDP», который на мобильных сетях душат по умолчанию. QUIC/HTTP/3 единственный UDP-класс, который нельзя заблокировать целиком, не сломав половину рунета. Значит, делаем HTTP/3-транспорт, неотличимый от браузера на том уровне, который DPI видит.

## 2. Что DPI видит в QUIC, а что нет

- Initial-пакеты шифруются ключами, выводимыми из публичного DCID, то есть DPI читает ClientHello полностью: SNI, ALPN, список шифров и расширений, QUIC transport parameters, размер и паддинг Initial. Это единственное место, где нас можно отличить от Chrome по содержимому.
- Handshake и 1-RTT пакеты непрозрачны: сертификат сервера, HTTP/3-фреймы, наша аутентификация и framing невидимы. Внутренний формат можно выбирать по удобству, на обнаружение он не влияет.
- Видимы метаданные: размеры и тайминги пакетов, направление, длительность, число соединений, IP сервера, ответ сервера на чужие подключения (активный пробинг).

Отсюда три рычага: Initial байт-в-байт как у текущего Chrome, одно долгоживущее соединение, настоящий сайт для всех, кто не наш клиент.

## 3. Дизайн

### Провод
- QUIC v1 (RFC 9000) на UDP/443, TLS 1.3 с настоящим сертификатом Let's Encrypt для нашего домена, ALPN `h3`. Не REALITY-подход с чужим SNI: для QUIC домен должен резолвиться в наш IP, иначе это само по себе признак.
- ClientHello клиента повторяет Chrome 155 для QUIC (JA4 вида `q13d0310h3_…`): шифры, расширения, GREASE, `quic_transport_parameters` (набор, значения, порядок), размер и паддинг Initial, длина DCID. Делается тем же хуком `client_hello_rewriter` из нашего форка rustls: quinn строит ClientHello через `emit_client_hello_for_retry`, где хук уже стоит. Эталон снимаем с настоящего Chrome 155 (pcap + `ja4plus`).
- Congestion control: Cubic по умолчанию (как у Chrome), BBR опцией. Без Brutal: его постоянная скорость без пауз это и есть сигнатура Hysteria.
- Один QUIC-connection на сервер, все TCP-цели как bidirectional streams, UDP как QUIC DATAGRAM (RFC 9221, Chrome использует их в WebTransport). Переподключение с backoff; ротация соединения не чаще раза в N минут и никогда больше одного handshake одновременно.

### Сервер (новый бинарник `vproxy-server`, тот же workspace)
- quinn-эндпоинт на 443/udp плюс HTTPS на 443/tcp (hyper) с тем же сертификатом: сайт отдаётся по TCP с заголовком `Alt-Svc: h3=":443"`, то есть домен выглядит как обычный сайт с HTTP/3, как его и находят браузеры.
- Сертификат автоматически через ACME (`rustls-acme`), либо файлы.
- Маскировка: статическая папка или reverse proxy на настоящий сайт. Любой неаутентифицированный клиент получает сайт и по QUIC, и по TCP, активный пробинг видит сайт.
- Аутентификация: первый bidirectional stream клиента начинается с 32 байт `HMAC-SHA256(key = SHA-256(uuid), msg = TLS-exporter("vproxy h3 auth", 32))`. Токен привязан к TLS-сессии, повтор бесполезен. Сравнение за константное время; несовпадение означает, что stream отдаётся HTTP/3-обработчику сайта, то есть «не наш» клиент просто смотрит сайт.
- После аутентификации framing простой: заголовок stream `[тип адреса][адрес][порт]`, далее байты; датаграммы `[session id varint][адрес][порт][payload]`. Пользователи списком uuid, счётчики трафика в логе. Outbound с той же политикой приватных адресов, что в vproxy.
- `vproxy-server service install` на основе нашего systemd-кода, Docker-образ.

### Клиент (vproxy)
- Новый outbound `h3` рядом с VLESS: quinn + форк rustls + профиль отпечатка `ChromeQuic_155`. Ссылка вида `h3://<uuid>@host:443?sni=domain#name`, подписки и `server.txt` как сейчас.
- Входит в `--ping` и автовыбор: если UDP в сети мёртв, выбирается REALITY. Это и есть «инструмент»: один клиент, два пути, выбор по месту.
- Нужные крейты: quinn 0.11 (на rustls 0.23, совместим с форком), rustls-acme 0.15, hyper. Для обычных HTTP/3-запросов используем библиотеку `h3` с адаптером quinn; ручной реализации SETTINGS/QPACK не планируем. Клиентский framing пока собственный. Конкретный сайт разворачивается из отдельного закрытого репозитория; публичный сервер содержит только универсальный обработчик.

### Чего сознательно не делаем в первой версии
- Salamander-подобную обфускацию: превращает QUIC в неизвестный UDP и убирает единственное преимущество.
- Port hopping: по данным 2026 ТСПУ ловит по форме трафика, а не по порту; добавим, только если тесты покажут блокировку конкретного порта.
- MASQUE/CONNECT-UDP совместимость: внутренний формат DPI не видит, стандарт не добавляет скрытности, только код.

## 4. Гипотезы для тестировщиков

Каждую проверять с нескольких сетей (мобильные МТС/МегаФон/Билайн/T2/Yota, проводные Ростелеком/Дом.ru и т. д.), с указанием региона и времени, по 3 прогона, пауза между прогонами ≥ 10 минут (заморозка 120-600 с привязана к IP клиента и SNI). Фиксировать: работает / скорость / заморозка после N МБ или N с / таймаут handshake.

| # | Гипотеза | Как проверить | Что решает |
|---|---|---|---|
| H0 | Отпечаток Chrome 133 (наш текущий `fp=chrome`) штрафуется, Chrome 155 нет | vproxy с REALITY, тот же сервер, `fp=chrome` старой и новой сборки; время handshake, таймауты | Нужно ли срочно обновлять отпечаток TCP-пути (делаем в любом случае) |
| H1 | QUIC на UDP/443 к зарубежному VPS вообще проходит | Настоящий Chrome открывает наш тестовый сайт по HTTP/3 (`chrome://net-export` или DevTools Protocol = h3) | Для каких сетей транспорт применим, где сразу fallback на REALITY |
| H2 | Длинный поток QUIC не душат и не морозят по объёму | Chrome качает файл 1 ГБ с тестового сайта по h3; график скорости, момент остановки | Есть ли волюметрический порог для «настоящего» HTTP/3 с нашего IP |
| H3 | Неизвестный UDP хуже, чем QUIC | iperf3 UDP на тот же VPS (10 Мбит/с, 2 минуты) против H2 | Подтверждает выбор QUIC против raw UDP |
| H4 | Hysteria 2 без Salamander с маскировкой работает; Brutal хуже Cubic/BBR; TUIC работает | Официальные клиенты, те же сети, 1 ГБ через прокси | Если H2 проходит, а Hysteria нет, значит есть сигнатура именно реализации: собственная реализация имеет смысл |
| H5 | QUIC-отпечаток клиента важен | Прототип (стадия 2): quinn по умолчанию против Chrome-профиля | Сколько вкладывать в мимикрию Initial |
| H6 | Больше 3 параллельных QUIC-handshake к одному SNI морозят | Прототип: 1 соединение против 4 одновременных | Жёсткость правила «одно соединение» |
| H7 | Репутация AS хостера решает | Та же сборка на Hetzner и на малоизвестном хостере | Рекомендации по хостингу, границы возможного |
| H8 | Сервер пробят активно | Логи сервера после недели использования: подключения с российских IP, не похожие на наших клиентов | Достаточно ли маскировки сайтом |

## 5. Стадии

0. **Chrome 155 для TCP-пути** (сразу, независимо от QUIC). Профиль из uTLS `HelloChrome_155`, обновить `src/protocol/fingerprint.rs` и тест JA4. Тестировщики проверяют H0.
1. **Измерения без кода** (параллельно со стадией 2, не блокирует её). Домен, VPS с Caddy (HTTP/3 из коробки, сертификат сам), файлы 10 МБ и 1 ГБ, Hysteria 2 с маскировкой на тот же Caddy в двух вариантах (Brutal/BBR), iperf3: всё это собрано в `deploy/trial-server/` (`setup.sh домен`, `docker compose up -d`); выбор провайдера, настройка VPS и порядок прогона — в [`trial-server-runbook.md`](trial-server-runbook.md). Тестировщики запускают `scripts/tspu-trial.sh`: он сам проходит H1, H2, H3, H6 (через curl с HTTP/3) и H0 (две REALITY-ссылки через vproxy), пишет отчёт в формате страницы испытаний; H4 (официальные клиенты Hysteria/TUIC) и подтверждение настоящим Chrome остаются ручными. Второй домен у другого хостера тем же скриптом даёт H7. Результат: матрица «сеть × тест», по ней приоритеты стадии 2 и 4.
2. **Прототип** (2-3 недели). Сделано: шаг 1 — каркас: `crates/core/src/h3/` (протокол и клиент на quinn), сервер `crates/server/` (`vproxy-server`), ссылки `h3://`, маршрутизация через `ProxyClient`, e2e-тесты в `crates/server/tests/e2e.rs`; шаг 2 — UDP как QUIC DATAGRAM (сессия на поток, начальный MTU 1350); переезд соединения при смене сети; фрагментация UDP-пакетов больше лимита датаграммы (на Теле2 после перехода на сотовую лимит падал до 1129 байт, и QUIC-пакеты приложений от 1200 байт терялись). Дальше: выбор Cubic/BBR (по первым замерам стенда BBR в 4-5 раз быстрее TCP на том же пути), отпечаток Chrome для Initial, деплой на стенд. Клиентский outbound на quinn с хуком отпечатка, минимальный сервер (сертификат файлами, статическая маскировка), аутентификация, TCP-streams, UDP-датаграммы, e2e-тест клиент-сервер в репозитории (здесь свой сервер окупается сразу: REALITY так тестировать нельзя). Снять Chrome 155 QUIC Initial, довести JA4 до совпадения. Тестировщики: H5, H6, повтор H2 уже через наш транспорт.
3. **Продукт**. ACME, TCP 443 с Alt-Svc, reverse-proxy маскировка, пользователи, `service install`, Docker, ссылка и подписка, автовыбор с REALITY, документация. Релиз.
4. **Закалка по данным**. HTTP/3-преамбула после handshake (настоящие SETTINGS/QPACK-streams и GET главной страницы, чтобы первые пакеты по размерам и таймингам были загрузкой страницы), паддинг мелких фреймов, ограничение симметрии, ротация соединений, цикл обновления отпечатка (как недельный sync форка rustls), port hopping только по результатам.

## 6. Риски

- Сети с полностью закрытым UDP (~5% провайдеров, корпоративные сети): транспорт не работает, спасает только автовыбор REALITY. Это принимаем.
- Репутация IP: если H7 покажет, что хостер решает всё, никакая мимикрия не поможет, и рекомендация станет «хостер вне списков».
- Chrome меняет QUIC-поведение чаще, чем TLS: нужна дисциплина обновления профиля, иначе через полгода мы «Chrome 133 для QUIC».
- Форма потока: если ТСПУ действительно ловит прокси по ratio и отсутствию пауз, стадия 4 станет основной работой, а не доработкой.
